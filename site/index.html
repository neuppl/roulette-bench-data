Benchmarking results summary🔗

These plots were generated on Friday, September 4th, 2026, from commit 6883a34: probalog: order base-fact variables by breadth-first traversal Variables were created in whatever order the facts happened to be written. For a representation with a total variable order that is the order it tests them in, and the cost depends on how far apart related variables sit: the diagram must keep alive every decision still relevant below the current level. Rule bodies join on shared variables, which bind to shared constants, so two facts naming the same constant are exactly the ones that can meet in a derivation. builds the graph of which constants share a fact, walks it breadth-first, and sorts the facts by their earliest-visited argument. It looks only at which facts share a constant and never at what a constant is, so renaming the data does not change the result – confirmed by permuting node labels, which moves a sort-by-argument order by 2x and this one not at all. The chorded ring, previously the worst case, at n=16 (ms, total): term (before BDD guards) 2661 bdd, declaration order 6576 bdd, this order 438 so 15x against the unordered version and 6x against the original implementation. smokers n=14 32 -> 24, ring n=60 960 -> 822, dag (6,5) 494 -> 468. dag (6,6) improves 5420 -> 3676 but still trails term’s 1532: a wide converging DAG is the shape where compiling the accumulated formula once at the end genuinely wins. Elimination orders were tried first and are the wrong tool. min-fill and min-degree minimise treewidth, which is the parameter for a vtree-structured representation such as an SDD; a total variable order is a path decomposition, so the parameter is pathwidth. Measured on chordring n=14: BFS 279ms, min-fill 615ms, min-degree 931ms, declaration 954ms. Both elimination orders were tried in both directions. Term backend unchanged in behaviour. 165 term tests and 118 BDD tests pass. Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>

Benchmarks are organized into groups, one per subdirectory of a run’s data folder. Each group gets its own section below, and within a section every benchmark that group produced is shown — including any nested in subdirectories of the group, which are flattened in and identified by file name. The plots are generated from the data in the data/ directory.

Each ordinary benchmark is shown with three plots side-by-side — timing (real, cpu and gc time), number of recursive calls, and total size — each tracked across benchmark runs.

Scaling benchmarks (those produced by the scale form) are rendered differently: their metrics are reported across a series of expressions from the most recent run rather than across runs. They appear inline within whichever group they belong to, mixed among the ordinary benchmarks, and are flagged with a (scaling benchmark) tag next to their name.

Maximum-argument benchmarks (those produced by the max-arg form) are also rendered specially: a single plot tracking the largest feasible argument across runs. They too appear inline within their group, flagged with a (max-arg benchmark) tag.

Additionally, there are benchmarks for the code profiler in the Extra plots section. These are generated from the files in the extra directory and are not part of the normal benchmarking data.

You can find these files and data in the roulette-bench-data repository.

These benchmarks are re-generated with each commit to the roulette repository.
